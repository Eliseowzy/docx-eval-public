## 一句话结论

**NimbleOffice 在换行结构（按篇平均 79.6% vs WorkBuddy 72.1%，差 +7.5pp ［+3.9, +11.3］）、行宽（67.7% vs 52.3%）和分页（页数与 Word 一致 66.9% vs 49.2%，差 +17.8pp ［+8.5, +27.1］）上都显著领先 WorkBuddy；千问办公（50.8%，无分页）排第三。** 协议头条“按行加权”上 NimbleOffice 74.6% vs WorkBuddy 48.0%，但这个差距主要来自两篇 6000 行以上政务表格在 8 并发下的 120 秒超时；事后单并发补测两篇都能出分，代入后 WorkBuddy 为 61.6%，差距的 95% CI ［−9.5, +37.2］ 跨 0。因此按行加权不宜作为对外主论据，按篇平均与分页才是稳健结论。NimbleOffice 也有 8 篇出现字形裁切（另两家为 0），见“NimbleOffice 自身的问题”。

## 头条稳健性：072/073 两篇超时

协议头条（按行加权、失败记 0）NimbleOffice − WorkBuddy = +26.6pp，但 072（6,432 行）与 073（7,537 行）占全部 Word 行的 31.7%，WorkBuddy 正好在这两篇上超时。为判断这是引擎能力还是评测条件造成的，事后做了两项**补充分析（不替代预登记头条）**：

1. **去掉这两篇（118 篇）**：按行加权 NimbleOffice 76.2% ［71.9, 80.1］、WorkBuddy 70.2% ［65.1, 75.2］、千问 44.9%；NimbleOffice − WorkBuddy = +6.0pp ［+2.4, +9.9］，显著。
2. **WorkBuddy 单并发补测这两篇**（run `hz-tx-j1-0723`，`-j 1`，同一 SDK 与 120s 上限）：两篇合计约 80 秒全部出分，未超时。说明正式 run 的超时是 8 并发下的资源争用，不是 WorkBuddy 处理不了。补测结构一致率：073 为 15.7%（NimbleOffice 99.3%），072 为 74.9%（NimbleOffice 38.2%）。代入后 120 篇按行加权 WorkBuddy 61.6%、按篇平均 72.8%；NimbleOffice − WorkBuddy 按行加权差 +13.0pp，95% CI ［−9.5, +37.2］，**不显著**。

结论：按行加权的大幅领先对两篇文档高度敏感，不应作为对外主论据；按篇平均（+7.5pp，补测后约 +6.8pp）、去掉两篇后的按行加权（+6.0pp）和分页（+17.8pp）三者方向一致且显著，是更稳的表述。今后对比测评建议各引擎单独、同并发度运行。

## 引擎版本与评测器改动（必须披露）

**NimbleOffice 的提交不是 `origin/main`。** 当时本机在旧 BetterOffice 检出中运行 `git rev-parse --short origin/main`，得到 `00352fab`，但它是 2026-11-05 的上游快照，与当时开发分支 HEAD 分叉：HEAD 有 142 个提交不在其中，它只有 1 个提交不在 HEAD；用它等于评测另一个引擎。按 PROTOCOL“封存点之前最新的 baseline 提交，前提是开发集 0 退步”，改用当时的开发分支 HEAD（早于封存提交），并在 848 篇开发集上与上一基线对比：**0 退步、26 改善、0 缺失**。该结果留档在 `runs/dev-65549f0e`。评测所用代码现以公开提交 `65549f0e` 发布。


评测器改动（每条都在受影响引擎的最终 run 之前完成；WorkBuddy 最终 run 早于第 4 条的 ASCII 写出，但该条只影响千问的代理对序列化，不改变已有 cmp 的分数）：

1. `harness/engines/*.py` 的每篇超时默认值从 300s 改为协议规定的 **120s**。
2. WorkBuddy 适配器：首轮 86/120 因本机网络代理在 8 并发下连接失败而中止；Chrome 改为不走代理，并对字体 CDN 的**瞬时**资源加载失败做有界重试（仍受同一 120s 预算约束）。资源加载失败会让腾讯渲染器悄悄落到 fallback 字体，原适配器把它判为“不是引擎测量”并失败，这一语义保留。
3. 两个 Chrome 适配器的超时清理原本访问不存在的 `TimeoutExpired.pid`；改为 `Popen` + `communicate` + 按进程组 `killpg`，避免超时后留下孤儿 Chrome 影响后续文档。
4. 千问适配器的 UTF-16 代理对（emoji 等）以两个独立 char 返回，写 `cmp.json` 时触发 `UnicodeEncodeError`；现在合并代理对、替换残留孤立代理字符，并把 `cmp.json` 改为 ASCII 转义写出。
5. `harness/flow_score.py` 原来会丢弃没有引擎输出的文档，且只给“差值”置信区间；现在按协议把失败文档以 0 分保留在同题集，并给按行加权指标加成对 bootstrap 95% CI。

**运行事故与恢复。** 最终用于报告的是 `hz-nimble`、`hz-tx`、`hz-qw` 三次完整 run，三家各一次有效评测。全部评测调用（含作废尝试）均有日志留存：首轮 WorkBuddy 因代理故障 86 篇失败；首轮千问因 UTF-16 代理对（surrogate pair）序列化崩溃；中间一次 NimbleOffice 重跑是在数十个孤儿 Chrome 仍在跑时做的，073 超时，清理后重跑与首轮干净结果逐项相同（120 篇、0 失败、pages 65.83%、lines 29.97%、defects 6256）。作废尝试不是引擎评分，没有因为分数高低挑选运行，也没有剔除任何文档。

## 稳定性与复现

- NimbleOffice：两次干净运行（首轮与最终轮）的 totals 完全一致（120 篇、0 errors、pageParity 65.83%、lineParity 29.97%、6,256 defects），固定 commit + 固定字体表。
- WorkBuddy：最终轮 118/120，两篇 6,000+ 行政务表格在 8 并发下两轮都 120s 超时；单并发补测（`hz-tx-j1-0723`）两篇共约 80 秒完成。
- 千问办公：120/120，0 报错；同一批次内没有出现提取截断（`flow_score` 的行数比 1.10 与按行加权 37.4% 一致）。
- 三家都使用同一份 Word 基准和同一份字体索引；Run 的 `meta.json` 记录了引擎版本和 Word 版本。

## 结论

1. **NimbleOffice 在这批中文真实文档上排第一**：按篇 79.6%、行宽 67.7%、字号 83.0%，页数与 Word 一致 66.9%（WorkBuddy 49.2%）；在党政公文、政务表格、高校论文三类结构一致率都超过 75%。短板是 8 篇字形裁切，以及与开发集相比明显的泛化落差。
2. **WorkBuddy 的行级细节不差，弱在分页和行宽**：按篇平均 72.1%，行左端误差 1.84pt（优于 NimbleOffice），但页数一致只有 49.2%、行宽 52.3%。正式 run 中两篇 6,000+ 行政务表格在 8 并发下 120s 超时，按协议记 0、按行加权 48.0%；单并发补测两篇均能出分，故这一失分应视为评测条件所致，不作为它的能力结论。
3. **千问办公排第三**：50.8% / 37.4%，行宽 41.1%、字号 63.8%；缺字体文档上掉到 48.6%，且本地 SDK 无分页，页数类指标不可比。它的域芯片影响只有 0.1 个百分点，不构成排序理由。
4. WPS 文档占 59.2%，三家在 WPS 层的排序与整体一致（NimbleOffice > WorkBuddy > 千问）；Word 层 WorkBuddy 的按行加权被 073 一篇拖到 45.0%，是这批数据里最大的单篇影响。
